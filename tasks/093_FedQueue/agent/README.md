# FedQueue: queue-aware federated learning on MNIST

The judge retrains submitted code from scratch and compares its hidden evaluation
accuracy with an archived baseline under the same benchmark protocol.

## 1. Goal

Research question: when stochastic queue delays decide when each client can compute
and return an update, can a federated server protect training by predicting those
delays online, budgeting local work from the prediction, admitting updates by
deadline and down-weighting stale ones?

The paper's controlled experiments (Section 6.2, Appendix E) compare FedQueue with
FedAvg, FedAsync, FedBuff and FedCompass on one shared workload. They fix the
optimizer, batch size, evaluation cadence and per-round resource requests, and confine
differences to orchestration, budgeting, admission and aggregation. Appendix E.4,
Table 12 repeats the comparison against FedAvg and FedCompass under stronger non-IID
data and reports max accuracy, time to 85% accuracy and total local steps.

Improve `accuracy` (higher is better) for that strong non-IID FedQueue setting. Four
clients have heterogeneous class distributions, generated by APPFL's two-Dirichlet
partition with alpha1=8 and alpha2=0.1. Queue delays are lognormal with sigma=0.9 and
client means 1.5/2.5/3.5/4.5 seconds. The training run has 50 target aggregation
rounds. This task scores accuracy only: time to target is not scored, and local steps
enter through the work guard in section 3.

## Research contract

**Objective.** Improve validation-selected MNIST accuracy by optimizing the fixed
CNN/cross-entropy federated workload under the same queue, communication-round and
local-work controls.

**Fixed research objects.** These define the shared workload and the regime under test.

- Table-9 SimpleCNN: two 3x3 convolutions (32/64 channels), two 2x2 max pools, FC
  3136-to-128, ReLU, dropout 0.5 and a ten-class head. Cross-entropy objective and the
  original pixels/255 input convention. The work counter uses minibatch size 64 (with
  ordinary short terminal batches); changing batch granularity cannot create extra
  uncounted work.
- Four clients, the supplied two-Dirichlet partition, exogenous lognormal queue draws
  and genuine compute-time feedback. Do not change clocks, queue delays or accounting.
- 50 target rounds and total scheduler local steps at most 1.2 times the frozen
  baseline mean, counting all returned `Ek` records including shutdown work. The
  original checkpoint selection and accuracy rules still apply.

**Editable methods.** Local optimizer, learning rates, aggregation, admission,
scheduling and implementation for this fixed objective within those controls. Baseline
optimizer, learning rates and admission heuristics are solving strategies and may
change while retaining the same objective and work definitions. The paper fixes the
optimizer across its methods; this task does not.

**Forbidden substitutions.** Queue delays stay unknown until a client reports them: budgeting and admission may use only delays already observed, not the queue RNG, its seed, or a delay sampled for the current round.

- Replacing the CNN or objective, changing batch granularity to obtain more work,
  centralizing client data, or changing the client or queue processes.
- Exceeding the local-work budget, or selecting checkpoints using hidden labels.
- Training or fitting reusable model state or learned preprocessing on validation
  features or labels, including final train+val refits or validation-based distillation.
- Replacing real elapsed-time feedback with a simulated clock.

## 2. Data

- `data/train/train.npz`: 48,000 labeled images, `id`, `x`, `y`.
- `data/val/input.npz` and `data/val/labels.npz`: 12,000 validation images and
  public labels. This is a stratified 20% holdout from the original training data,
  materialized with split seed 20261030 before client partitioning. `labels.npz` also
  holds the scalar `baseline_mean_total_local_steps`.
- Images are uint8 arrays of shape [N,28,28]; labels are digits 0–9. Training and validation IDs are
  original row numbers within their source, sorted increasingly. The baseline
  uses float32 pixels divided by 255, without augmentation or normalization.
- The evaluation split is held by the judge and follows the same image schema.
  It is never accessible here. Predict solely from supplied images; IDs identify
  rows and must not be used to reconstruct or memorize labels.
- The baseline and candidates train only on `data/train`, including final fits,
  within the same client and communication protocol. Declare
  `training_source: "train"` in the model card and apply the partitioner only
  to training rows. During a training run, validation only selects the checkpoint.
  Additional refit rounds are not allowed. External data, relabeling, and changing the
  fixed validation set are prohibited.

## 3. Metric and scoring

`accuracy = 100 * mean(predicted_class == label)`. The paper's test-based best-round
selection is replaced with validation-based selection: choose the earliest highest
validation-accuracy checkpoint among rounds 1–50. Only that checkpoint is evaluated
on new inputs. The harness averages the scores across five training seeds.

| Guard | Enforced by |
|---|---|
| Prediction CSV header, field types, and one row per input ID in increasing order | validator |
| `total_local_steps` at most 1.2 x 14244.8 = 17093.76, counting shutdown work | scorer on the declared value; probe recounts `Ek`; patch audit for real execution |
| `rounds` 50, `clients` 4, `protocol` `fedqueue-alpha01-rho09-v1`, `selected_round` in 1–50 | scorer on declared values; probe replays traces; patch audit for real execution |
| APPFL alpha1=8, alpha2=0.1 partition with BENCH_SEED | probe; patch audit |
| Exogenous queue constants in `bench/protocol.py` and genuine compute-time feedback | probe replays queue settings and draws; feedback needs patch audit |
| Validation-only checkpoint selection and predictions from the saved artifact | probe; patch audit |
| Fixed SimpleCNN/cross-entropy workload and minibatch-64 step-counting convention | probe replays the fixed model; objective and work semantics need patch audit |
| `training_source: "train"` | probe checks the card; patch audit checks actual data use |
| No hidden or external data, no fabricated work logs or certificates | patch audit |

A scorer violation produces `accuracy: Infinity`, which the harness treats as failure;
`manifest_score: 0` records the paper rule's worst score. The scorer sees only declared
values, and the certificate is not proof of actual execution. The probe is
`bench/check_model.py`. The harness does not run it automatically, so these rules also
rely on patch audit. You can run it yourself as documented in `bench/io_spec.md`;
`bench eval-dev --keep` keeps the model directory it needs.

Baseline validation accuracy is 84.9317% (population standard deviation 5.3128
percentage points across five seeds). For seeds 1–5 it is 86.875, 77.85, 80.65, 86.14
and 93.14, using 12851–13380 local steps. `bench status` exposes the measured baseline.
PASS uses relative gain at least `max(delta, 2 * baseline_seed_std / abs(baseline_mean))`;
delta is 0.04. The judge computes this on the evaluation split. At the validation
figures above the noise term is about 0.125, well above delta. Seed variance is
substantial for this asynchronous experiment.

## 4. Baseline

Official repository: <https://github.com/APPFL/APPFL>, upstream commit
`6477b8371caae13c0983033b3970379f8db17176`. The supplied runtime source
is under `code/src/appfl`.
`code/experiment/model_cnn.py` is the reproduced paper CNN: two padded 3x3 convolutions
(32/64 channels), max pooling, a 128-unit dense layer, dropout 0.5, ten outputs.
Training uses cross entropy, Adam and the Table 9 configuration in
`code/experiment/configs/`: base learning rate 0.003, batch size 64, T_sync 10 seconds,
safety buffer 2, admission tolerance 0.2, EWMA rate 0.5, harmonic staleness decay with
beta 0.5. Those files still say Dirichlet alpha=0.5; `code/main.py` and
`code/partition.py` apply alpha2=0.1. The actual training, aggregation and scheduling
implementations are `VanillaTrainer`, `FedQueueAggregator`, and `QueueScheduler` under
`code/src/appfl/algorithm`.

The baseline provides offline data loading, BENCH_SEED propagation, validation
checkpoint selection, model export, and train/predict entry points.
The baseline keeps the reproduced model, loss, hyperparameters, training loop and
scheduler behavior. The scheduler uses real wall time; identical seeds can still
have different asynchronous arrival orders and local-step allocations.

At the 16-CPU task budget, measured training including validation selection
took 15.78–17.75 minutes per seed. Prediction on the validation input took
10.98–11.64 seconds.
Each independent training run retains the reproduction's four-core affinity and
one compute thread per process. The baseline does not need all 16 cores.

## 5. Interface (frozen)

- `bash code/train.sh --out DIR`: train and save the predictor, all checkpoint
  selection evidence, and `model_card.json` in DIR.
- `bash code/predict.sh --model DIR --input PATH --output FILE`: predict from the
  supplied NPZ and write CSV at the exact FILE path. See `bench/io_spec.md`.
- Honor `BENCH_SEED`, `BENCH_CPUS`, `BENCH_DATA_DIR`, and `BENCH_BENCH_DIR`.
  Client RNGs in the baseline use BENCH_SEED plus the zero-based client index.
- Dependencies are pinned in `code/env.lock`. Only `name==version` pins from
  PyPI / PyTorch CPU are rebuildable; editable, git and local installs fail.

## 6. Rules

The work and method rules are in the research contract above.

`data/`, `bench/`, this README, entry-point signatures and prediction schema are
frozen. The model certificate and logs must describe the actual completed run.
All files needed for inference belong in `--out`; prediction must not train or
modify its artifact after seeing evaluation inputs.

The task has 16 CPUs and a 16 GB memory limit. The judge uses five
seeds, 1–5; every run must honor BENCH_SEED.

Reading, reconstructing or guessing hidden labels, embedding memorized predictions,
using external training data, and bypassing the work/queue protocol disqualify a
submission.

## 7. Known pitfalls

- Accuracy varies with both seeds and real execution timings, and an unchanged rerun
  of a seed can give a different score. The client partition also changes with the
  seed. Evaluate changes on multiple seeds with `bench eval-dev --seed S`; without
  `--seed` it runs seed 0, which the judge does not use. Do not replace real
  elapsed-time feedback with a simulated clock.
- `code/main.py` pins each run to the first four allowed cores, so concurrent runs share
  cores and slow each other, which changes the compute-time feedback.
- Preserve absolute path handling and PYTHONPATH setup: the harness sets
  PYTHONSAFEPATH=1 and invokes scripts from a clean clone of the committed code.
- gRPC is local only; use an unused loopback port and clean up child processes.
- All 50 checkpoints must exist before validation selection. An extra shutdown
  checkpoint is allowed by the original implementation but cannot be selected.
- Output paths may have no CSV extension. Write the exact supplied path.
- Input/data/bench mounts are read-only; write artifacts into `--out` or temporary
  storage. Never download MNIST at runtime or load it from an installed package.

## Validation use (baseline and candidates)

Fit models and learned preprocessing only on the designated training observations.
Validation features and labels are for evaluation and method, hyperparameter or
checkpoint selection only. This restriction applies equally to the baseline and
every candidate, including final retraining. Do not merge validation into training,
fit normalization/encoders on validation, distill from validation predictions, or
relabel validation observations as training or calibration data.

For tasks defined as per-instance inference, optimization or online interaction,
use only the observation/training/calibration/feedback roles explicitly specified
for that instance. Do not use its evaluation targets or carry fitted state from
validation cases into other independent cases. A development replay directory may
contain separately designated training observations; its validation observations
remain excluded from fitting. Public visibility does not authorize training use.
